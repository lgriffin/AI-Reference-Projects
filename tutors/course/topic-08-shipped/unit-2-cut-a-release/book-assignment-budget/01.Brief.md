# Brief

Work in `$LADDER/variants/rung-7-shipped` (or your scratch release repository from the lab).

## What to build

1. **A measure.** Add `largest-page-bytes` to `MEASURES` in `scripts/lib/slo.ts`. It reads the size of the
   largest `.html` file the build wrote. Not `tutors.json`, not `version.json`: those are not pages a learner
   opens. Its advice, when the budget is exceeded, names the largest pages, largest first, so the reader
   knows where to look.
2. **An objective.** Add an objective to `release/slo.yaml` with `measure: largest-page-bytes`, an `id`, a
   `budget` in bytes and a `why`. Choose the budget from a measurement: run `pnpm release:slo` first and
   leave honest headroom. For the fixture, 16 kB or less.
3. **Evidence.** Write a test in `scripts/tests/slo.test.ts` that exercises `largest-page-bytes`: at least
   one case where `tutors.json` is the largest file and the measure still reports the largest page.
4. **A claim.** Add a claim with `id: pages-within-budget` to `release/claims.yaml`, whose evidence is your
   test.

## What not to change

- `evaluate` in `scripts/lib/slo.ts`: the teaching message for a breach is already there; your measure's
  `advice` fills in the middle of it.
- The other objectives' budgets, the fence, the architecture tests and the grading test.

## Upstream

Upstream budgets the reader's JavaScript and CSS per route (`scripts/checks/bundle-budget.ts`, the
`bundle-budgets` job in `ci.yml`) and judges its SLOs per app (`release/slo.yaml`). Read
`scripts/checks/bundle-budget.ts` in `$MONO` before you write the advice: how does upstream tell a
contributor which chunk grew?
