# Check the SLOs

~~~bash
pnpm release:slo
~~~

~~~
ok   build-time: the time to build the fixture site is 88 ms, within its budget of 2000 ms (96% headroom).
ok   site-size: the size of the whole site is 15.0 kB, within its budget of 24.4 kB (38% headroom).
~~~

The script builds the fixture three times with the real command, as a separate process, and keeps the
slowest time: a budget should hold on a bad day.

## Exceed a budget

~~~bash
sed -i.bak 's/budget: 25000/budget: 10000/' release/slo.yaml
pnpm release:slo; echo "exit $?"
~~~

~~~
FAIL SLO "site-size" exceeded: the size of the whole site is 15.0 kB, over its budget of 9.8 kB by 5.3 kB (54%). The largest files are tutors.json (5.0 kB), topic-01-basics/index.html (1.6 kB), index.html (1.3 kB). Shrink what is not value to a learner (repeated markup, unused styles). If the growth is value a learner gets, raise the budget in release/slo.yaml in its own pull request that says why. Never raise a budget to make a release pass: a budget is a ratchet, as upstream's slo/floors.yaml in the release harness is.
exit 1
~~~

~~~bash
mv release/slo.yaml.bak release/slo.yaml
~~~

## Why time is not in the gate

`scripts/tests/slo.test.ts` judges the size budget inside `pnpm test`, but not the time budget. Read the
comment in the test that says why. What would happen to a team whose gate failed one run in twenty
because a laptop was busy?
