# Explore upstream's architecture tests

Read these in your clone of tutors-mono-repo. Answer each question in a sentence or two.

## The layers as configuration

Open `.dependency-cruiser.cjs`.

1. `LAYERS` lists seven layers. Which layer holds every `packages/jsr/*` package?
2. `layerRules` is built from `LAYERS` with `slice(index + 1)`. Explain in your own words how one entry
   becomes one rule.
3. Find `course-rules-no-file-system`. What does `dependencyTypes: ["core"]` forbid? Check that it holds:

~~~bash
grep -rn '"node:' $MONO/packages/jsr/course-rules/src
~~~

   No output. Compare it with rung 3's Port rule.

## Rules that are proven to bite

Open `tests/architecture/dependency-rules.test.ts` and list `tests/architecture/fixtures/workspace`.

4. Pick one row of the `it.each` table. Find the fixture file it names, and the import that breaks the
   rule.
5. What does the test "does not flag downward imports or a cycle inside one package" protect against?
6. Rung 3 has no negative fixtures; this lab is its negative fixture, done by hand. Sketch how you would
   add one to rung 3: where would the fake workspace live, and how would `architecture.test.ts` point at it?

## The ratchet

Open `tests/architecture/known-violations.txt` and `scripts/checks/lib/ratchet.ts`.

7. What happens when someone fixes the `layer-core` violation listed there but forgets to delete the line?
   Find the message in `describeRatchet`.
8. Why is a ratchet better than allowing the old violation forever in the rule itself?

## Run it, if your install allows

With a full install of the mono-repo (Node.js 26.13 or later and `pnpm install`, as in the Orientation lab):

~~~bash
cd $MONO
pnpm architecture-report
~~~

How many violations does it report? Compare them with `known-violations.txt`. Then run
`pnpm test:runway` and find the architecture tests in its output.
