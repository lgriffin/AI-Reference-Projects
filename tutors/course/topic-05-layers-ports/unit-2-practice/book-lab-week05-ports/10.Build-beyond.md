# Build beyond (Create)

Pick two. Each starts from the value it adds. Keep `pnpm test` green, the arrows inward and the platform at
the edge. Changes to `tests/architecture/`, the fence or a `tsconfig.json` are yours to make, not your
agent's, and go in a commit of their own with the reason.

1. **A real zip adapter.** Value: a lecturer can build a course straight from a downloaded zip. Finish
   `ZipFileSystem` without a library, using `node:zlib`'s `inflateRawSync` and the zip central directory.
   It needs `node:` modules, so it lives in `apps/cli`, not `gen`. Make the contract green for it.
2. **A browser adapter, on paper.** Value: rung 5's reader could validate a course in the browser. Sketch a
   `FetchFileSystem` over HTTP for a course published with a file listing. Which methods are hard? What does
   the Rung Fence say today, and which rung lifts it?
3. **Negative fixtures for rung 3.** Value: every rule proves, on every run, that it can fail. Add a tiny
   fake workspace under `tests/architecture/fixtures/` that breaks each rule once, and make the architecture
   test run each rule against it, as upstream's `dependency-rules.test.ts` does.
4. **A ratchet.** Value: a team could adopt a new rule without fixing everything first. Add
   `tests/architecture/known-violations.txt` and change `none(...)` so a listed violation is allowed, a new
   one fails, and a listed one that no longer occurs fails too. Use upstream's `scripts/checks/lib/ratchet.ts`
   as your model.
