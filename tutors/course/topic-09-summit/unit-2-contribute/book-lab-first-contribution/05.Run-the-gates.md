# Run the repository's gates

## The minimum bar

CONTRIBUTING.md and the pull request template ask for three commands before any PR that touches code:

~~~bash
pnpm lint    # ESLint; errors fail CI, the several hundred existing warnings do not, but add none
pnpm test    # vitest: unit, BDD steps, component, contract and the repo-level checks
pnpm check   # svelte-check on the apps; clean on main, so any error is yours
~~~

`pnpm test` includes three platform conformance tests that need `kubectl` or `kustomize`.

## The runway tier

`pnpm test:runway` runs the repository-level suites on their own: `tests/architecture`,
`tests/suite-health`, `tests/completeness`, `tests/observability`, `tests/conformance`, `tests/security` and
`tests/performance` (see `package.json`). It is a quick way to check you have not crossed a layer boundary or
left a baseline out of step.

~~~bash
pnpm test:runway
~~~

## When a gate is red

Read the message before you ask the agent to fix it. Most of the repository's checks name the rule, the
offender and the fix.

- **A baseline line no longer occurs.** Your fix removed a known problem. Delete its line from the baseline,
  in the same PR.
- **Coverage sits 2 or more points above a floor.** Raise the floor in
  `tests/suite-health/coverage-floors.json`, in the same PR.
- **A new dependency rule violation.** Your change crossed a layer. Do not add it to
  `known-violations.txt`; that file may only shrink. Move the code instead.
- **A test you did not write fails.** Stop. This is on your "Ask a human first" list.

## Optional: what CI will run

The table "What CI checks on your pull request" in CONTRIBUTING.md lists every CI job and its local command,
such as `pnpm check:knip`, `pnpm test:ears:audit` and `pnpm test:mutation:pr`. You are not expected to run them
all. If CI fails on one, a maintainer will help you read it.
