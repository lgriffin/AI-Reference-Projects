# Open the pull request

## Commit

Use the conventional commit style from CONTRIBUTING.md:

~~~
fix: short description

Optional longer description explaining the change.
~~~

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `security`, `perf`.

## Title, with its artefact hint

If a student, lecturer or operator could observe the change, the PR title names what it moves, in a trailing
parenthesis, using the release harness's vocabulary:

~~~
fix(reader): raise nav contrast (axe, dom)
~~~

No hint means "nothing observable should differ". `changelog-hint.yml` checks the hint against your diff. On
a fork it cannot fix the title for you, so it fails and its log gives the exact title to use; edit the title
and it runs again.

## The template

GitHub fills in `.github/PULL_REQUEST_TEMPLATE.md`. Fill it in honestly:

- what changed and why, with "Closes #<n>"
- the three local checks you ran
- for a UI change, a screenshot, light and dark mode, and keyboard reachability
- for a behaviour change, the test and the EARS Rule id
- "Anything the reviewer should know": say you worked with a coding agent, and that you read and can explain
  every line. Unsure is fine; say so.

## After you open it

- On your first PR, GitHub may hold the workflow runs until a maintainer approves them.
- A merge needs one approving review and a green **CI success** check.
- CONTRIBUTING.md aims for first review feedback within five business days.
- Respond to review as a conversation. If the reviewer asks for something no check caught, note it: that rule
  is at L0 or L2, and moving it up a level is a good second contribution.
