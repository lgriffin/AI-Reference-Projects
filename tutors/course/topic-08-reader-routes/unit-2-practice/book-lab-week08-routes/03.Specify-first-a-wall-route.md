# Specify first: a wall route (Evaluate, Create)

From week 7 on, every lab opens the same way: a requirement and a scenario, in the variant, before any
code. This is the first time you do it for a user interface.

## The need

A student revising for an exam says: "I want all the labs of this course on one page." Today the reader
makes them open each topic in turn. Upstream has a page for exactly this, the **wall**
(`$MONO/apps/reader/src/routes/(course-reader)/wall/[type]/[courseid]/`): every learning object of one
kind in a course. Rung 5 does not have it.

This is a **pulled** feature: a named customer, a stated need, and a page that ends when the need is met.
Before writing a word, decide the scope with the same care. Which kinds get a wall? Rung 5 has pages for
talks, notes and labs, so those three, and no others.

## 2. The Rule and its scenarios

Add to the end of `tests/bdd/features/reader/reader.feature` (keep the two-space indent of the other
Rules, and copy the sentence word for word):

~~~gherkin
  @R-022 @ears-event-driven
  Rule: When a wall of talks, notes or labs is opened for a course, the reader shall show every learning object of that kind that the course holds.

    Scenario: The wall of labs
      Given a host that serves upstream's tutors.json for the shared fixture as the course "walls"
      When a learner opens "/wall/lab/walls"
      Then the wall shows the lab "Lab-01-First-Steps"

    Scenario: The wall of talks
      Given a host that serves upstream's tutors.json for the shared fixture as the course "walls"
      When a learner opens "/wall/talk/walls"
      Then the wall shows the talk "Welcome"
~~~

The route is `/wall/<kind>/<course id>`, as upstream's: the kind comes before the course id. The `Given`
and the `When` are steps the feature already uses. Only the `Then` is new.

## 3. Bind the steps

In `tests/bdd/steps/reader/reader.steps.ts`, add `Wall` to the type import from `course-service.ts`:

~~~ts
import type { PageRequest, Wall } from "../../../../apps/reader/src/lib/course/course-service.ts";
~~~

and add this Rule just before the file's last line (`});`):

~~~ts
  Rule("When a wall of talks, notes or labs is opened for a course, the reader shall show every learning object of that kind that the course holds.", ({ RuleScenario }) => {
    for (const title of ["The wall of labs", "The wall of talks"]) {
      RuleScenario(title, ({ Given, When, Then }) => {
        Given("a host that serves upstream's tutors.json for the shared fixture as the course {string}", serving);
        When("a learner opens {string}", (_ctx, paths: string) => opens(paths));
        Then("the wall shows the {word} {string}", (_ctx, kind: string, titles: string) => {
          const page = pages.at(-1)!;
          if ("notFound" in page) throw new Error(page.notFound);
          const wall = page.found as Wall;
          expect([wall.kind, wall.los.map((lo) => lo.title)]).toEqual([kind, list(titles)]);
        });
      });
    }
  });
~~~

"A learner opens" calls `openPage` in `tests/bdd/support/reader.ts`, which stands in for SvelteKit's router.
Teach it the new route. Import `requestWall` beside `requestLab` and `requestLo`, and change the start of
`openPage` to:

~~~ts
  const [, kind, courseId = "", third = ""] = path.split("/");
  // /wall/<type>/<courseid>: as upstream, a wall's route names the kind before the course id.
  if (kind === "wall") return requestWall(courseId, third, fetch);
  switch (kind) {
~~~

(For a wall the second segment is the kind and the third is the course id, so `requestWall(kind, courseId,
fetch)` receives them in that order.)
