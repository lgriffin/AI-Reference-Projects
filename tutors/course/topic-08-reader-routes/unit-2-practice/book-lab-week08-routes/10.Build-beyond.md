# Build beyond (Create)

Pick two. Each starts from a student's need, so each starts with "Specify first": take the next id, write
the EARS sentence, add the Rule and a scenario, see red, then build. Stay inside the fence: no new
dependency, no server code, no storage. Keep `pnpm test` green.

1. **A wall that says it is empty.** Value: a student who opens "All notes" in a course with no notes
   should be told so, not shown a heading over nothing. Decide the behaviour (a message? a 404?) and say
   why in one line before you write the requirement. Which EARS pattern fits: Unwanted behaviour or
   State-driven?
2. **Walls only where there is something to show.** Value: no dead links in the top bar. Show a wall link
   only for a kind the course holds. Put the decision in `lib/course` (a function from tree to kinds), not
   in the component, and prove it with a scenario on a course you build in the step.
3. **A unit's own address.** Value: a lecturer can send a link to one unit ("do unit 2 before Tuesday").
   A unit has no page, but `Units.svelte` gives each box `id={unit.id}`. Specify and build
   `/topic/<course>/<topic>#<unit id>` as the place a unit's breadcrumb links to. What can a scenario prove
   here, and what needs a browser?
4. **Your own course.** Value: you, reading your own material. Run
   `node apps/cli/src/main.ts --json-only <your course> apps/reader/static/courses/mine` on the course you
   wrote in week 1, then open `/course/mine`. List what the reader shows for kinds rung 5 does not build,
   and write the requirement for the one you miss most.

For each extension, write down first: **who** asked for it, and **what they can do afterwards** that they
could not do before. If you cannot answer, it is overproduction, and the kindest thing is not to build it.
