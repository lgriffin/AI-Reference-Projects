# Kaizen (Evaluate)

Ten minutes, as every week. This week's Lean focus is **value to the student reader**, and **pull, not
push**.

## Name one waste

Candidates from this week:

- **Inventory.** After step 7 part 3 you had a working wall page no student could reach. How long did it
  stay that way? In a real team, what makes that gap grow from minutes to weeks?
- **Waiting.** How long is the gate now, compared with rung 4's? Which part grew: `svelte-check`, the
  tests, or the build? Did you run the whole gate when `pnpm test:bdd` would have answered your question?
- **Partially done work.** You committed a red specification in step 3 and it stayed red for three steps.
  Was that honest, or was it in the way? What is the longest a red commit should live?
- **Relearning.** Did an example or an agent hand you `$lib`, `svelte.config.js` or `+page.server.ts`?
  What told you it was wrong, and how quickly?
- **Overproduction.** Did you add anything to the wall that R-022 did not ask for?

## Find its root cause

Ask "why?" until you reach something in the standard work that you can change: the gate, `AGENTS.md`,
`README.md`'s "Extension points" table, a rule's message, or your own habit.

## Improve the standard work

Make or propose one change. Examples:

- a row in `AGENTS.md`'s "Where things go" table: "a page: specify it, build the logic, the route, **and a
  link to it**, in one change";
- a script, `"test:reader": "vitest run tests/unit/reader tests/bdd/steps/reader"`, for the fast loop while
  you work on the reader (adding a script is not adding a dependency, but check the fence agrees);
- a note in your own checklist: "write the sentence, then ask who pulled it".

Record the waste, the root cause and the change in your learning log with this week's date. Next week
starts from the reader as you leave it today, so commit:

~~~bash
git status          # clean?
git log --oneline   # "rung 5, as shipped", the red specification, the wall
~~~
