# Name the rule (Evaluate, Create)

From week 6 every new capability starts as a requirement written in **EARS** (the Easy Approach to
Requirements Syntax). You start practising now, informally. An EARS requirement is one sentence with one
"shall", and a small set of patterns for when it applies:

| Pattern | Shape |
| --- | --- |
| Ubiquitous | The `<system>` shall `<response>`. |
| Event-driven | When `<trigger>`, the `<system>` shall `<response>`. |
| State-driven | While `<state>`, the `<system>` shall `<response>`. |
| Unwanted behaviour | If `<condition>`, then the `<system>` shall `<response>`. |
| Optional feature | Where `<feature>`, the `<system>` shall `<response>`. |

## This week's rule

This week you met one rule from two sides: the generator leaves out a folder whose name has no kind, and the
validator reports it. Here is one way to write each half:

> **R1.** When a folder's name starts with no learning-object kind, the generator shall leave the folder and
> everything inside it out of `tutors.json`.
>
> **R2.** If a folder that holds course material has a name that starts with no learning-object kind, then the
> validator shall report an error that names the folder and the fix.

## Your turn

Write two more rules of your own, in your notes, about what you saw today. Suggestions:

1. how a web link's `route` is found (event-driven: "When a `web` folder holds a `weburl` file, ...");
2. what rung 1 does when there is no `course.md` (unwanted behaviour: "If ..., then the generator shall ...").

Then judge each of your sentences against three questions:

- Does it have exactly one "shall"?
- Could a test decide whether it holds? Write the test's name in one line.
- Which Assertion Ladder level keeps it today, in rung 1 or upstream? (L0 if nothing does.)

Keep the sentences. In week 6 you will turn rules like these into `REQUIREMENTS.md` entries with ids.
