# Map the value stream (Analyse, Evaluate)

You have now done steps 1 to 8 of the SOP by hand, one at a time. This step measures them. A value stream
map follows one release down the line and writes two numbers at each station: **process time** (work is
being done) and **waiting** (the release sits). Their sum is the **lead time**.

pnpm release:value-stream

## Add mutation testing

The SOP's step 5 includes mutation testing, which the default run leaves out because it takes minutes:

~~~bash
pnpm release:value-stream --with mutation
~~~

On the machine that wrote this lab it took 2 min 21 s, 80% of a process time of 2 min 56 s. One step is
four fifths of the work. Is that waste? Before you answer, say what the step buys (the reading note,
"What the Closure Check closes"), and how often it needs to run: on every commit, or once per release?

## Add the waiting

A machine waits for nobody. A release does. Recall your own last piece of group work, or use this story:
the captain ran the checks at five in the evening, the claims needed an hour's fix by a contributor who
was in a lecture, and the reviewer read the A3 at nine the next morning.

~~~bash
pnpm release:value-stream --only claims,slo,readiness --wait claims=3600 --wait readiness=57600
~~~

what the script cannot see.

## Draw the map

On paper, draw one box per step, left to right, in SOP order. Under each box write its process time. On
the arrow into each box write the wait. Use the full run's process times and the story's waits. Under the
line, total both:

Compute the flow efficiency yourself: process time over lead time. It is about 0.3%.

## Find the waste

Answer from your map, with numbers:

1. **Where is the time?** Which single change would shorten the lead time most: a faster gate, a faster
   mutation run, or a reviewer who is told the moment the A3 is ready?
2. **What is done twice?** Run `grep -n "pnpm build" package.json`. The reader is built by `pnpm test`,
   again by `pnpm test:e2e`, and again by `pnpm release:slo`. Time one build (`time pnpm build`): about
   three seconds here. How much of the process time is rebuilding something that had not changed? Each
   script is right to build when run alone. What would you change, and what would you risk?
3. **What waits on one person?** In the story, two waits were for a person. Which could a tool shorten
   (a notification, a CI job that runs the checks on every push), and which should stay a person's time?

## Stop the line

Break a budget and run the stream again:

~~~bash
sed -i.bak 's/budget: 25000/budget: 16000/' release/slo.yaml
pnpm release:value-stream --only claims,slo,container,readiness; echo "exit $?"
mv release/slo.yaml.bak release/slo.yaml
~~~

~~~
| 5 | Release claims | 6 | `pnpm release:claims` | - | 0.3 s | 8% | passed |
| 6 | Service level objectives | 7 | `pnpm release:slo` | - | 3.6 s | 92% | failed |
| 7 | Build and smoke the image | 8 | `pnpm container:smoke` | - | - |  | not run |
| 8 | The readiness A3 | 9 | `pnpm release:readiness` | - | - |  | not run |
...
- **The line stopped at slo.** Later steps did not run: a failed step is fixed before the release moves on (release/SOP.md, "Stop the line").
exit 1
~~~

"Not run" is not "skipped" and not "passed". Read R-044 in `REQUIREMENTS.md`, then open
`scripts/lib/value-stream.ts` and find `runSteps`. Why is the arithmetic a pure function, with the
processes started somewhere else? (Which architecture rule says so?)

Finish with a clean, full run, so that the next step reads fresh numbers:

~~~bash
pnpm release:value-stream
~~~
