# Experiment upstream (Analyse)

Now see the same ideas at full scale. Read, do not change. Everything here is in tutors-mono-repo (`$MONO`,
pinned at `2b96b69`) and a clone of the release harness:

~~~bash
git clone https://github.com/tutors-sdk/tutors-release-harness.git ~/src/tutors-release-harness
export HARNESS=~/src/tutors-release-harness
~~~

Upstream asks for Node 26.13 or later; every part of this step also works by reading.

## 1. The release SOP

Open `$MONO/release/SOP.md`. It has twelve steps and three roles. For each of your ten steps, find the
upstream step it corresponds to. Then list the upstream steps you had no counterpart for. Which exist
because Tutors has a production to compare with (a clean A/A, rehearsals, a watch window)?

Find "Stop the line (andon)". Which rule forbids re-running for a better number, and what is a re-run
allowed to do? Compare with rung 7's "Stop the line": which of its six rules has no upstream twin, and
why?

## 2. A claim there and a claim here

Open `$MONO/release/claims.yaml` and `$MONO/release/README.md`. Pick one claim and say, in one sentence,
what difference from production it waives. Then compare with one of rung 7's claims: what does each kind
of claim make the release *do* when it is wrong?

If you installed upstream's dependencies in an earlier week, run its Closure Check:

~~~bash
cd $MONO && pnpm check:release-claims
~~~

~~~
OK: release/claims.yaml is valid (12 claims).
~~~

Open `$MONO/scripts/checks/release-claims.ts`. What must a claim's `rule` resolve to? Where does rung 7's
check look for the same kind of thing?

## 3. The release strategy

Open `$MONO/guides/Release-Strategy.md`. Read "Principles" and "Changelog Discipline". Then read "4. Final
Release" and find the paragraph about 3 November 2026. In your own words: what happened, what did the
harness judge that night, and what is the countermeasure? Is the countermeasure a reminder or a change to
the system?

## 4. The candidate ships

Read the header comment of `$MONO/.github/workflows/image-build.yml`, then open
`$MONO/scripts/promote-image.ts` and find `REBUILT_NOTICE`. Rung 7 builds its image where it smokes it.
Upstream refuses to: it promotes the image the harness judged. Which checks must hold before a candidate
is promoted, and which one would catch a rebuild from the same source with a newer base image?

## 5. What is production?

Open `$MONO/release/deployed.json`. Which tag is deployed, from which commit, and how is each app named?
Compare it with your `version.json`: both answer "which build is this?". Why does upstream answer with a
digest per image where rung 7 answers with a commit?

## 6. Lean, as the harness writes it

Read `$HARNESS/docs/lean.md`: "The five ideas", the bands of the Release Confidence Score, and the section
on the A3. Find the sentence that says what happens to a number the inputs cannot show. Where did you see
the same rule in rung 7 today (two places)?

Then read `$HARNESS/kaizen/README.md`, "What opens a 5 Whys", and look at one file in `$HARNESS/kaizen/`.
A 5 Whys there ends in one countermeasure of seven kinds. Which kind would you choose for a claim that
kept losing its evidence?
