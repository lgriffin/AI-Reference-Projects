# The readiness A3 and the tag (Evaluate)

Steps 9 and 10 of the SOP. One page, one reader, one decision.

~~~bash
pnpm release:readiness
~~~

~~~
**READY, with one check not run.** Nothing stands between this commit and a tag.
wrote .../rung-7-shipped/out/readiness.md
~~~

Open `out/readiness.md` and read it top to bottom. It should take two minutes.

| Section | What it holds |
| --- | --- |
| 1. Background | the value in this release: your curated changelog section |
| 2. Current condition | each check, its standard, where it stands now, and the command that measured it |
| 3. Goal | what "ready" means, in one sentence |
| 4. Root cause analysis | each gap, and the prompt to ask why until the answer is a process or a tool |
| 5. Countermeasures | one per gap |
| 6. Plan | the SOP's steps, ticked when done; the last is always a person's |
| 7. Follow-up | what to compare next release |

Every row names its source. Which check did not run? If you ran `--with mutation` in step 7 and have not
committed since, your Mutation row shows the score. If you skipped the container, that row reads "not
run" too: a pass for another commit says nothing about this one.

## Judge it

You are the Reviewer, a second person who wrote none of the commits. Swap with a neighbour if you can.
Before you say "ready", answer in writing:

1. Background: does the changelog section say what a user gets, or does it repeat commit messages?
2. Is "READY, with one check not run" good enough to tag? What would you need to know about the check
   that did not run? Would your answer differ for a patch release with one fix?
3. The Lead time row says 36 seconds. Is that this release's lead time? What is missing from it?
4. Pick the row with the least headroom. What would have to happen for it to fail next release?

## Make it hold

Edit any file and run it again without committing:

~~~bash
echo "" >> README.md
pnpm release:readiness
~~~

~~~
**HOLD.** 1 gap(s) stand between this commit and a tag; each is under Root cause.
~~~

Open the page again and read sections 4 and 5:

~~~
1. **Source.** The working tree has uncommitted changes, so no commit is what would ship.
...
| 1 | Source | Commit or stash, then run this again: a release is a commit, not a folder. |
~~~

Check the exit status (`echo $?`): it is 0 even on HOLD. The A3 is advisory by design. What decides,
then? And why would a page that could fail the release be worse? Undo the edit (`git checkout README.md`).

## Tag it

This is step 10, and it is yours. In your working repository only:

~~~bash
pnpm test
git tag v1.1.0
git log --oneline --decorate -3
~~~

~~~
dab0743 (HEAD -> main, tag: v1.1.0) chore(release): 1.1.0
aa1f783 Update notes
f6b0309 feat(cli): print the usage with --help
~~~

Nothing in rung 7 can run this for you: the fence fails any script that runs `git tag` or `git push`. Try
it. Add this line to the end of `scripts/release-version.ts` and run the fence:

~~~ts
export const tag = () => execFileSync("git", ["tag", "v1.1.0"]);
~~~

~~~bash
pnpm exec vitest run tests/rung-fence.test.ts
~~~

~~~
AssertionError: Rung Fence, rung 7 (Shipped): scripts/release-version.ts uses git push or git tag ("tag"). Tagging and pushing a release is a person's act (release/SOP.md, step 10: the Human Boundary). A script prints the command; a person runs it.
~~~

Undo it (`git checkout scripts`). Upstream draws the line in the same place: its workflow tags only
candidates, and the final `vX.Y.Z` is tagged by hand.
