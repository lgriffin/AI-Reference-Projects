# The container (Apply, Analyse)

Step 8 of the SOP. The last piece of evidence is that the thing runs. Read the `Dockerfile` first. Two
stages: Node builds the fixture site, BusyBox serves it. Find the two digests, the `USER` line and the
labels.

## Without Docker

See exactly what the smoke check would run:

~~~bash
pnpm container:smoke --dry-run
~~~

~~~
docker build -q -f Dockerfile -t tutors-ladder:1.1.0 --build-arg VERSION=1.1.0 --build-arg GIT_SHA=dab074367ea22c791c82259e12e34379330f016d ..
docker run -d --rm --read-only --cap-drop ALL --security-opt no-new-privileges -p 127.0.0.1::8080 tutors-ladder:1.1.0
container smoke: SKIPPED: dry run: commands printed, none run
~~~

The build context is `..`, the folder that holds `rung-7-shipped` and `fixtures`.
`Dockerfile.dockerignore` sends only what the build stage copies. With Docker installed but no daemon
running, the real command skips and says why:

~~~
container smoke: SKIPPED: docker is installed but no daemon answers (...). The image was not built or checked; run this where Docker runs (CI does), or use --dry-run to see the commands.
~~~

It exits 0, and step 8 will show the A3 saying "not run". Why is `SKIPPED` with exit 0 honest here, when a
skipped test was not acceptable as evidence in step 5?

## With Docker

~~~bash
pnpm container:smoke
~~~

~~~
container smoke: PASSED: every check passed
  ok user is 10001:10001, not root
  ok revision label is dab0743
  ok /version.json answers 1.1.0 at dab0743
  ok /index.html is served, with its Content Security Policy
  ok /tutors.json is served and parses
~~~

Five facts, and each ties back to something earlier: the user to this step, the revision and the version
to step 3's build identity, the policy to week 10's last wall, `tutors.json` to week 1's contract.

If Docker Hub refuses the pull with a rate limit, pull the same digests from a mirror:

~~~bash
LADDER_REGISTRY=mirror.gcr.io/library pnpm container:smoke
~~~

The digest still decides the bytes: a mirror that served different ones would fail the pull.

## Try it as a person would

~~~bash
docker run --rm --read-only --cap-drop ALL -p 127.0.0.1:8080:8080 tutors-ladder:1.1.0
~~~

Open `http://127.0.0.1:8080/` and `http://127.0.0.1:8080/version.json`. Stop it with Ctrl-C, then:

~~~bash
docker image inspect tutors-ladder:1.1.0 --format '{{.Size}} {{.Config.User}}'
~~~

~~~
6854852 10001:10001
~~~

About 7 MB. The image holds a static site and one small server, and nothing that built them.

## Break it

Change `USER 10001:10001` to `USER 0` in the `Dockerfile`:

~~~bash
pnpm exec vitest run tests/release/dockerfile.test.ts
pnpm container:smoke; echo "exit $?"
~~~

~~~
AssertionError: User rule: UID 0 is root. A flaw in a server that runs as root owns the container.
...
container smoke: FAILED: the image runs as "0". A server runs as a user that is not root (USER 10001:10001 in the Dockerfile), so a flaw in it cannot own the container.
exit 1
~~~

Two checks caught one mistake: a test that reads the file, in the gate, and a check that asks the built
image. Which would catch a base image that sets its own `USER`? Which runs on a laptop with no Docker?

Now remove `@sha256:...` from one `FROM` line and run the test again. Read the Digest rule's message: what
can a tag do that a digest cannot? Put both back with `git checkout Dockerfile`.

## The CI template

Open `.github/workflows/ladder-ci.yml`. It sits in a subfolder, so GitHub does not run it. Find the five
jobs and the one job that needs them all. Then change one `uses:` line from its SHA to `@v7` and run:

~~~bash
pnpm exec vitest run tests/release/workflow.test.ts
~~~

Read the Pinning rule's message, and undo the change. The file is inactive, yet three tests hold it to
its rules. Why test a template nobody runs?
