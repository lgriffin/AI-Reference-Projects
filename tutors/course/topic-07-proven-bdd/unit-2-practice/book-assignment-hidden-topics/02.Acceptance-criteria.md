# Acceptance criteria

Written as EARS sentences, one "shall" each. Each maps to a module outcome in `course.md`; all are assessed at
**Create**, because together they are one rule you specify, build and prove.

| Id | Criterion | Module outcome |
| --- | --- | --- |
| AC1 | `REQUIREMENTS.md` shall hold an Event-driven requirement that names `properties.yaml`, `ignore` and `hide`, implemented in gen. | M6 |
| AC2 | The EARS audit shall report no finding, and a Rule tagged with the requirement's id shall have at least one scenario. | M6 |
| AC3 | When `properties.yaml` lists topics under `ignore`, the generator shall write exactly those topics with `hide` set to true. | M4, M6 |
| AC4 | If a course has no `properties.yaml`, or no `ignore` key, then the generator shall hide no topic, and it shall never leave a topic out. | M4, M6 |
| AC5 | A file in `tests/fuzz/` shall cite the requirement's id and shall hold a "... can fail" negative fixture. | M6 |
| AC6 | When `pnpm test:mutation` has run after the change, every mutated file shall meet its floor in `tests/mutation/mutation-floors.json`. | M6 |
| AC7 | When `pnpm test` is run, the variant shall pass, with the conformance and golden tests unchanged. | M4 |
| AC8 | The history shall show the requirement committed before the implementation. | M6 |

AC1 to AC6 are checked by the grading test in the next step. AC7 is the variant's own gate. AC8 is read by
a person.
