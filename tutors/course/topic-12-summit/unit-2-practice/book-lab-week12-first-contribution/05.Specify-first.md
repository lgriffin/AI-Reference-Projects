# Specify first (Create)

Since week 7 every lab has begun with a requirement and a scenario, added before any code. Upstream works
the same way, with two differences. There is no `REQUIREMENTS.md`: the requirement **is** the `Rule:` title
in a feature file. And the ids are four digits, `@rule-NNNN`, not `R-NNN`.

Read `.claude/skills/ears-gherkin-dev/SKILL.md` and its `references/ears-rules.md` now. They are short.

## 1. Does your change need a Rule?

The skill's test: "If a change alters what a person or the release harness would observe, it needs a Rule."
Refactors, docs edits and "fixes that restore behaviour an existing Rule already states" do not.

- **Behaviour changes**: you need a Rule in the pull request. Do all of this step in your branch.
- **No behaviour changes** (the walkthrough fix is one): no Rule goes in the pull request. Do this step
  anyway, in a scratch file, for the rule your finding broke. It becomes the root cause section of your A3,
  and perhaps your second contribution.

## 2. Search first

~~~bash
cd $MONO && grep -rn "walkthrough" tests/bdd/features | head
~~~

At the pinned commit this prints nothing: no Rule mentions the walkthrough. If a Rule already states your
behaviour, you change that Rule and keep its id. Never add a second one.

## 3. Take an id

~~~bash
pnpm test:ears:audit --next-id
~~~

~~~
0786
~~~

(At the pinned commit; yours will be higher.) The audit only sees `main`, so search the open pull requests
for `@rule-` and take the next id none of them uses.

## 4. Write the Rule and one scenario

Copy the shape of `tests/bdd/features/developer/tutors-cli.feature`. Here is a worked example for the
walkthrough finding. Save yours as `~/src/my-rule.feature` if it is a scratch Rule:

~~~gherkin
@developer
Feature: Documented paths
  As a new contributor
  I want the walkthrough to name files that exist
  So that I can follow one page through the code without getting lost

  @rule-0786 @ears-ubiquitous
  Rule: Tutors shall name, in docs/COURSE-PAGE-WALKTHROUGH.md, only file paths that exist in the repository.

    Scenario: Every path the walkthrough names exists
      Given the course page walkthrough
      When each repository path in backticks is looked up
      Then every one of them exists
~~~

## 5. Let the audit critique it

~~~bash
pnpm test:ears:audit --strict ~/src/my-rule.feature
~~~

~~~
../my-rule.feature:2: unbound-feature: No steps file under tests/bdd/steps loads this feature with loadFeature("<literal path>").
FAIL: 1 feature file(s), 1 Rule(s), 1 new violation(s), 0 baselined, 0 stale baseline entries.
~~~

One finding, and it is the honest one: nothing proves the Rule yet. That is RED, part one, in the skill's
words. Now break the sentence on purpose. Change the title to
`The walkthrough should be accurate and shall name files and shall be up to date.` and run it again:

~~~
../my-rule.feature:8: obligation-keyword: Rule title uses "should"; the obligation keyword is "shall".
../my-rule.feature:8: shall-count: Rule title has 2 "shall"; a requirement has exactly one.
../my-rule.feature:8: system-name: The word before "shall" must be a system name: tutors, the reader, the catalogue, the live dashboard, the time dashboard, the data API.
~~~

Put the good title back.

## 6. Approve it yourself

The skill tells an agent to "show the Rule to the human and wait for a yes: the requirement is the thing
they are approving". You are the human. Read your Rule aloud. Could a reviewer who has never seen the code
tell whether it holds? If not, rewrite it before you go on.
