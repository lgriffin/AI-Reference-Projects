# Run the repository's gates (Analyse)

## 1. The minimum bar

CONTRIBUTING.md and the pull request template ask for three commands before any pull request that touches
code. Docs-only pull requests may skip them; run them once anyway, to see the Summit's gate.

~~~bash
pnpm lint    # ESLint; errors fail CI, the several hundred existing warnings do not, but add none
pnpm test    # vitest: unit, BDD steps, component, contract and the repo-level checks
pnpm check   # svelte-check on the apps; clean on main, so any error is yours
~~~

`pnpm test` includes three platform conformance tests that need `kubectl` or `kustomize`; without one they
fail with "Install kustomize or kubectl". That failure is yours to explain in the pull request, not to hide.

## 2. The runway tier

`pnpm test:runway` runs the repository-level suites on their own: `tests/architecture`, `tests/suite-health`,
`tests/completeness`, `tests/observability`, `tests/conformance`, `tests/security` and `tests/performance`.
It is a quick way to check you have not crossed a layer boundary or left a baseline out of step.

~~~bash
pnpm test:runway
~~~

For a behaviour change, also run the two commands the skill ends on:

~~~bash
pnpm test:bdd && pnpm test:ears:audit
~~~

The audit must end `0 new violation(s)`.

## 3. When a gate is red

Read the message before you ask the agent to fix it. Most of the repository's checks name the rule, the
offender and the fix. For each red you meet, write its Assertion Ladder level beside it: did it only fail
(L3), or did it also teach (L4)?

| The message says | What it means | What you do |
| --- | --- | --- |
| a baseline line no longer occurs | your fix removed a known problem | delete its line from the baseline, in the same pull request |
| coverage sits 2 or more points above a floor | your tests raised coverage | raise the floor in `tests/suite-health/coverage-floors.json`, in the same pull request |
| a new dependency rule violation | your change crossed a layer | move the code; never add a line to `known-violations.txt`, which may only shrink |
| a new module has no mutation floor | you added a library module | measure and add the floor (`guides/testing/MUTATION-TESTING.md`) |
| a test you did not write fails | unknown | stop: this is on your "Ask a human first" list |

## 4. Five Whys on one red

Pick one failure you met (or, if everything was green, the walkthrough drift itself) and ask why until you
reach something that could be changed. Keep the chain: it is the root cause section of your A3. Remember the
SOP's rule: "Human error" is never an answer; it is the prompt for the next why.

## 5. Optional: what CI will run

The table "What CI checks on your pull request" in CONTRIBUTING.md lists every CI job and its local command,
such as `pnpm check:knip`, `pnpm test:ears:audit` and `pnpm test:mutation:pr`. You are not expected to run
them all. If CI fails on one, a maintainer will help you read it.

**On rung 7.** The gate is `pnpm test`, then the release checks from week 11: `pnpm release:claims`,
`pnpm release:slo` and `pnpm release:readiness`.
