# Choose a small improvement (Evaluate)

Kaizen starts from a need somebody has. Find one.

## 1. Three candidates

Open the [`good first issue`](https://github.com/tutors-sdk/tutors-mono-repo/labels/good%20first%20issue)
list. CONTRIBUTING.md promises that each one "names the files to change, the expected result and how to check
it. Most touch one package and need no knowledge of the wider architecture."

Collect three candidates: two issues, and one finding of your own. You hold at least two findings already:

- the walkthrough drift from step 2 (`+layout.server.ts` is now `+layout.ts`);
- the generator crash on a course with no `properties.yaml`, from week 1's lab.

**Search before you claim.** For any finding of your own, search the open and closed issues and the open pull
requests first. Someone may have reported or fixed it, and upstream moves faster than this module:

~~~bash
gh search issues --repo tutors-sdk/tutors-mono-repo "layout.server"
gh search prs --repo tutors-sdk/tutors-mono-repo "COURSE-PAGE-WALKTHROUGH"
git -C $MONO fetch origin && git -C $MONO grep -n "layout.server" origin/main -- docs
~~~

If the last command prints nothing, it is fixed on `main`. Good: choose another.

## 2. Find the rung each one sits on

| The change touches | Its rung |
| --- | --- |
| docs only | weeks 1 and 2 |
| `packages/jsr/gen`, `packages/jsr/model`, `packages/jsr/tutors` | 1 Seed |
| `packages/jsr/tutors-lite` | 2 Lite |
| `pnpm-workspace.yaml`, `.dependency-cruiser.cjs`, `packages/jsr/types`, `packages/jsr/course-rules`, `tests/architecture` | 3 Layers |
| `tests/`, `tests/bdd/features`, `guides/testing`, `stryker.config.json` | 4 Proven |
| `apps/reader`, `packages/svelte/ui-*`, `packages/svelte/course`, `packages/svelte/utils/i18n` | 5 Reader |
| `packages/jsr/identity`, `packages/svelte/utils/rbac`, `packages/svelte/ui-primitives/src/utils/sanitize.ts`, `tests/security` | 6 Guarded |
| `.github/workflows`, `release/`, `Dockerfile`, `deploy/` | 7 Shipped |
| `supabase/`, `packages/jsr/realtime`, `packages/svelte/realtime-supabase`, `apps/live` | Summit only |

Take a candidate only if its rung is at or below the number you wrote down in step 1. If it spans two rungs,
you need both. If it is "Summit only", leave it for now: it needs Supabase or realtime knowledge that no rung
teaches.

## 3. Judge them

Score each candidate. This is the Evaluate work of the week, so write a reason beside each score.

| Question | Candidate A | Candidate B | Candidate C |
| --- | --- | --- | --- |
| **Value**: who is better off (student, lecturer, contributor, maintainer), and how would they notice? | | | |
| **Size**: how many files? Could you explain it to a friend in two sentences? | | | |
| **Rung**: at or below yours? | | | |
| **Check**: how will you, and the reviewer, know it worked? | | | |
| **Behaviour**: could a student, lecturer or operator observe the change? | | | |

Choose the one with clear value and the smallest size. When two tie, take the smaller.

## 4. Claim it

For an issue, comment "I'll take this". For a finding of your own, open an issue from the repository's
template (`.github/ISSUE_TEMPLATE/bug_report.yml`), say what you saw with the command and its output, and say
you would like to fix it.

## If upstream access is not possible

If you cannot use GitHub, or your candidate is fixed before you start, make the same kind of improvement to
rung 7 in your `~/src/tutors-ladder/rung-7-shipped`. Every later step has a rung 7 form, marked "On rung 7".
