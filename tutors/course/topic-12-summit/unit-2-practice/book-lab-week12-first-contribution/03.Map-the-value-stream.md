# Map the value stream of a pull request (Analyse)

In week 11 you mapped a release, from commit to running. This week's product is smaller: one merged pull
request. Sketch its value stream before you start, so that you know where the time will go.

## 1. The steps

Read `CONTRIBUTING.md` in `$MONO`, sections "Getting Started", "Making Changes" and "Pull Request Process",
and `.github/PULL_REQUEST_TEMPLATE.md`. Then copy this sketch into your notes and correct it from what you
read:

~~~
 [issue] -> [claim it] -> [branch] -> [Rule] -> [code] -> [3 local checks]
                                                               |
 [released] <- [merged] <- [review] <- [CI success] <- [pull request opened]
~~~

## 2. Work time and waiting time

For each step, estimate the **work time** (someone is improving the change) and the **waiting time** (the
change sits). Some facts from the repository to start you off:

| Step | What the repository says |
| --- | --- |
| claim it | for a good first issue, comment "I'll take this"; for anything larger, discuss the approach on the issue first |
| CI starts | "On your first PR, GitHub may hold the workflow runs until a maintainer approves them" |
| CI success | needs every job in `.github/workflows/ci.yml` |
| review | "We aim to provide initial review feedback within 5 business days"; typos and docs "typically merged within 2 business days" |
| merged | one approving review and a green **CI success** check |
| released | the changelog is written at release time from merged pull requests (`release/SOP.md`, step 3) |

Add both columns up. Your lead time is their sum. What fraction of it is work?

## 3. Find the waste

Mark each of these on your sketch where it could happen:

| Waste | In a pull request |
| --- | --- |
| Rework (defects) | CI fails on something a local check would have caught; a second review round |
| Waiting | for a reply, for workflow approval, for review |
| Extra features | a diff that touches files the issue never named |
| Handoffs | a description the reviewer has to ask questions about |
| Relearning | a rule the reviewer has to explain because nothing stated it |
| Partially done work | a branch with no pull request; a pull request nobody is answering |

## 4. Decide what you will do about it

You cannot shorten a maintainer's queue. You can make sure your change goes round the loop **once**. Write
three sentences of the form "I will ... so that ...". For example: "I will run the three local checks before
I push, so that CI does not find what I could have found." Keep them; the Kaizen step checks them.

## Check yourself

Which single step, done badly, causes the most rework downstream? (A hint from week 6: it is the cheapest
step to change.)
