# Open the pull request (Evaluate)

## 1. Title, with its artefact hint

If a student, lecturer or operator could observe the change, the title names what it moves, in a trailing
parenthesis, using the release harness's vocabulary (the table of hints is in CONTRIBUTING.md, "Changelog
Entries"):

~~~
fix(reader): raise nav contrast (axe, dom)
~~~

No hint means "nothing observable should differ". `.github/workflows/changelog-hint.yml` checks the hint
against your diff. On a fork it cannot fix the title for you, so it fails and its log gives the exact title
to use; edit the title and it runs again. A docs fix needs no hint:

~~~
docs: name the root +layout.ts in the course page walkthrough
~~~

## 2. Push and open

~~~bash
git push fork HEAD
gh pr create --repo tutors-sdk/tutors-mono-repo --web
~~~

## 3. The template

GitHub fills in `.github/PULL_REQUEST_TEMPLATE.md`. Fill it in honestly, and delete what does not apply:

- **What changed and why**, in one or two sentences, with "Closes #<n>";
- **Checks I ran locally**: tick only what you ran;
- for a UI change: a screenshot, light and dark mode, keyboard reachability;
- for a behaviour change: the test and the EARS Rule id, "a `@rule-NNNN` id no open PR uses";
- **Anything the reviewer should know**: say you worked with a coding agent, and that you read and can
  explain every line. "Unsure is fine; say so."

## 4. Review your own pull request first

Before you ask for a maintainer's time, be the reviewer. Open the "Files changed" tab and answer the
questions CONTRIBUTING.md says reviewers ask ("What We Look For"):

| Question | Your answer |
| --- | --- |
| Does the change solve the stated problem? | |
| Are there tests for new functionality? | |
| Does it follow existing code patterns and architecture? | |
| Is it accessible? | |
| Is it one logical change? | |

If any answer is "not quite", fix it now. That is one review round you have saved everybody.

## 5. After you open it

- On your first pull request, GitHub may hold the workflow runs until a maintainer approves them. Nothing is
  wrong if CI has not started.
- A merge needs one approving review and a green **CI success** check.
- Respond to review as a conversation. CONTRIBUTING.md: "This is collaborative, not adversarial."
- If the reviewer asks for something no check caught, note it: that rule is at L0 or L2, and moving it up a
  level is a good second contribution.

Write down the times: issue claimed, pull request opened, CI green, first review, merged. They complete the
value stream you sketched in step 3.

**On rung 7.** Open the pull request against your own repository, or write the description as a file,
`PR.md`, using upstream's template. Ask a classmate to review it with the five questions above.
