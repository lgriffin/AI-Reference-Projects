# Brief

## What to do

1. **Choose** a small real improvement to
   [tutors-sdk/tutors-mono-repo](https://github.com/tutors-sdk/tutors-mono-repo). It may be the one you
   started in the lab, a `good first issue`, a baseline line you can delete, or one of the lab's "Build
   beyond" extensions. It must sit on a rung you have finished. Search the issues and pull requests first, and
   claim it on its issue.
2. **Specify first.** Write the requirement as an EARS `Rule:` with at least one Given/When/Then scenario, in
   upstream's own style: a system name from the audit's list, exactly one "shall", an `@rule-NNNN` id and one
   `@ears-*` tag (see `tests/bdd/features` and `.claude/skills/ears-gherkin-dev/SKILL.md` in the mono-repo).
   If the change alters observable behaviour, the Rule goes in the pull request and you show it red before
   green. If it does not (docs, a refactor, a fix that restores an existing Rule), cite the existing Rule it
   restores, or write the Rule your finding broke as a scratch file, pass it through
   `pnpm test:ears:audit --strict`, and submit it beside the A3.
3. **Fence your agent** with a session manifest of under 500 words: Task, Rung, May touch, Must not touch,
   Read first, Gate, Ask a human first.
4. **Implement** the smallest change that satisfies the Rule. Keep `git diff --stat` inside "May touch".
5. **Run the gates**: `pnpm lint`, `pnpm test`, `pnpm check`, plus `pnpm test:bdd` and
   `pnpm test:ears:audit` for a behaviour change. Keep the output.
6. **Open the pull request** with upstream's template filled in honestly, including that you worked with an
   agent.
7. **Write the A3** (step 3 of this assignment): value, current state, root cause, countermeasure, evidence.
   One page.

## How small is small?

One logical change, reviewable in one sitting. As a guide: at most three source files and their tests, no new
dependency, nothing under `.github/CODEOWNERS`'s named paths (`.github/`, `release/claims.yaml`,
`release/SOP.md`, `SECURITY.md`). If your idea is bigger, contribute its first slice and say in the A3 what
would come next.

## Merged or not

The pull request does **not** have to be merged by the deadline. Review takes the time it takes, and you do
not control a maintainer's queue. You are assessed on what you submitted and how you responded to any review
you received, not on the merge button.

## If upstream access is not possible

If you cannot use GitHub, if your institution does not allow public contributions, or if your improvement is
fixed upstream before you finish, make the same kind of improvement to rung 7, in your
`~/src/tutors-ladder/rung-7-shipped`:

| Upstream | On rung 7 |
| --- | --- |
| a `Rule:` with an `@rule-NNNN` id in `tests/bdd/features` | a requirement with an `R-NNN` id in `REQUIREMENTS.md` and its `Rule:`, word for word, in `tests/bdd/features`; the closure audit green |
| your session manifest alone | the variant's `AGENTS.md` and Rung Fence, plus your session manifest |
| `pnpm lint`, `pnpm test`, `pnpm check` | `pnpm test`, then `pnpm release:claims`, `pnpm release:slo`, `pnpm release:readiness` |
| a pull request against upstream | a branch in your repository and a `PR.md` using upstream's template, reviewed by a classmate |

The marking is the same. Say in the A3 why you took this route. A rung 7 improvement that upstream would also
benefit from is ideal: say which upstream file it mirrors.

## What is not acceptable

- a change you cannot explain line by line;
- a test, baseline, floor or fence edited so that a gate goes green;
- a Rule written after the code and presented as written first (the commit history and the red run show the
  order);
- a pull request that ignores the repository's template or its code of conduct.
