# The grading tests

The grading tests are already in the variant, skipped until you ask for them:

| File | Checks |
| --- | --- |
| `tests/assignment/lo-pager.grading.test.ts` | AC1 and AC2 on your requirement and feature; AC3 and AC4 on upstream's `tutors.json` for the fixture; AC5's files; AC6's mutation run and floors |
| `tests/assignment/lo-pager.e2e.ts` | AC7 in Chromium: from the first talk, through the note, to the lab |

Run them with:

~~~bash
cd ~/ladder/rung5/tutors-ladder/rung-5-reader
pnpm test:assignment
~~~

That sets `LADDER_ASSIGNMENT=1`, runs the grading tests, and only if they pass builds the reader and runs
the browser check. Before you start, every grading test fails, and each message names the criterion and
the fix:

~~~
 × AC1: REQUIREMENTS.md states the reading-order rule in EARS, implemented in the reader
 × AC2: the requirement is proved by a scenario in the reader's feature, and the EARS audit is clean
 × AC3: the reading order is the course's talks, notes and labs, in pre-order
 × AC4: each stop knows its neighbours; the ends have one; a page that is not a stop has none
 × AC5: the pager is a navigator, shown on every talk, note and lab, with unit tests of its own
 × AC6: Stryker mutates lo-pager.ts, and a fresh report meets every floor

AssertionError: AC1: no requirement says "the reader shall" and "reading order". Specify first: add a row
with the next id (pnpm test:ears:audit --next-id).
...
AssertionError: AC5: put the pager's logic in apps/reader/src/lib/course/lo-pager.ts, plain TypeScript, so
Vitest and Stryker can run it.
...
      Tests  6 failed (6)
~~~

The tests are numbered in the order you should work: the requirement, the scenario, the logic, the
component, the mutation floor, the browser.

When you are done:

~~~
 Test Files  1 passed (1)
      Tests  6 passed (6)
...
 Test Files  1 passed (1)
      Tests  1 passed (1)
~~~

and `pnpm test` still shows the six grading tests as skipped and everything else passing.

## How the grading test reads your work

**Your requirement** is found by its words, not its id, so it does not matter which id you were given:

~~~ts
parseRequirements(...).find(({ text }) => /\breading order\b/i.test(text) && /\bthe reader shall\b/i.test(text));
~~~

**Your module** is imported by a computed path, so the gate compiles before the file exists:

~~~ts
const pager = (await import(/* @vite-ignore */ PAGER)) as Pager;
const { decorateCourseTree } = await import(/* @vite-ignore */ join(READER, "src", "lib", "course", "lo-tree.ts"));
return { pager, tree: decorateCourseTree(JSON.parse(readFileSync(ORACLE, "utf8")), "sample") };
~~~

`ORACLE` is `../fixtures/ladder-sample-course.tutors.json`, written by upstream's generator. Your pager is
graded against the contract, not against your own generator.

**Your mutation run** is read from `reports/mutation/mutation.json`, so AC6 needs a fresh
`pnpm test:mutation` after your last change to `lo-pager.ts` or its tests. Until the new file has a floor,
the gate itself is red, with a message that tells you what to run:

~~~
Mutation floor rule: tests/mutation/mutation-floors.json lists exactly the files in stryker.config.json's
mutate list. Run pnpm test:mutation, then pnpm check:mutation-floors --update.
~~~

**The browser check** finds the pager by its accessible name, so the label matters:

~~~ts
const pager = page.getByRole("navigation", { name: "Learning object pager" });
~~~
