# The grading test

The grading test is in the variant: `tests/assignment/hidden-topics.grading.test.ts`. `pnpm test` collects
it, so it skips unless you ask for it, and it compiles before your code exists (it reads `hide` through a
cast, and finds your requirement by its words, not its id).

~~~bash
cd tutors/variants/rung-5-proven
pnpm test:mutation                                 # AC6 reads the report this writes
LADDER_ASSIGNMENT=1 pnpm exec vitest run tests/assignment
~~~

Before you start, four of the six fail. AC4 and AC6 pass already: nothing is hidden yet, and the floors hold.
They are guards, so that a solution cannot pass by hiding too much or by losing mutation score. When you
are done:

~~~
 ✓ Assignment 06: hidden topics > AC1: REQUIREMENTS.md states the rule in EARS, event-driven, implemented in gen
 ...
      Tests  6 passed (6)
~~~

## What it checks

| Test | How |
| --- | --- |
| AC1 | parses `REQUIREMENTS.md` with the audit's own `parseRequirements` |
| AC2 | looks for `@<id>` in the features, then runs the whole audit and expects no finding |
| AC3 | builds courses in `MemoryFileSystem` with `ignore:` lists of one and two topics, the second followed by another key |
| AC4 | builds without `properties.yaml`, with `ignorepin:` (a different key upstream courses use), and checks every topic is still there |
| AC5 | reads `tests/fuzz/*` for the id and the words "can fail" |
| AC6 | reads `reports/mutation/mutation.json` and runs the floor check; a stale floor is allowed here, a low one is not |

Each failure names its criterion and the fix, as the gate's own checks do.
