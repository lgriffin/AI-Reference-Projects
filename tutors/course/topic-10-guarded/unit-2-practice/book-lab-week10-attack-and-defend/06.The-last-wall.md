# The last wall: Content Security Policy (Analyse, Evaluate)

Suppose a future change to lite lets a script through escaping and sanitising. Defence in depth says: assume
it will. The Content Security Policy is still there, enforced by the browser.

## The static site's policy

~~~bash
head -4 $LAB/rung-6/index.html
~~~

~~~html
<!doctype html>
<html lang="en">
<head><meta charset="utf-8">
<meta http-equiv="Content-Security-Policy" content="default-src &#39;none&#39;; img-src &#39;self&#39; https:; style-src &#39;sha256-uFXDLpKCWUzpfGMl1+wqTfnwqAJAOXhmjbj/FXjCahQ=&#39;; base-uri &#39;none&#39;; form-action &#39;none&#39;">
~~~

Now play the attacker who got past both walls. Inject script by hand:

~~~bash
sed 's#<main>#<main><script>alert("injected")</script><a id="j" href="javascript:alert(2)">j</a>#' \
  $LAB/rung-6/index.html > $LAB/rung-6/injected.html
~~~

Open `$LAB/rung-6/injected.html`, open the developer tools console, and click **j**. No alert. The console
says:

~~~
Executing inline script violates the following Content Security Policy directive 'default-src 'none''. ...
Running the JavaScript URL violates the following Content Security Policy directive 'default-src 'none''. ...
~~~

The page is still styled: its one inline style is allowed by its SHA-256 hash.

## Keep the hash honest

Change `max-width:52rem` to `max-width:53rem` in `STYLE` in `packages/lite/src/html.ts`, then:

~~~bash
pnpm vitest run tests/unit/lite/csp.test.ts
~~~

~~~
AssertionError: CSP rule: STYLE changed, so its hash in packages/lite/src/html.ts is stale and browsers would drop the style. Set STYLE_HASH = "sha256-mvxex1rzyPbfT6EwdmMmY9jtcPa3FUhM+ANQnQ5WaOw=". Never fix this with 'unsafe-inline': that would let an injected style or script tag through too.
~~~

A Teaching Failure: it gives the value to paste and names the tempting wrong fix. Undo with
`git checkout .`.

## The reader's policy

The reader cannot say "no script": it is one. The gate built it in step 5, so look at what it carries:

~~~bash
grep -o '<meta http-equiv="content-security-policy"[^>]*>' apps/reader/build/200.html
~~~

~~~
<meta http-equiv="content-security-policy" content="default-src 'none'; connect-src 'self'; img-src 'self' https:; script-src 'self' 'sha256-...'; style-src 'self'; style-src-attr 'unsafe-hashes' 'sha256-S8qMpvofolR8Mpjy4kQvEm7m1q8clzU4dfDH0AmvZjo='; base-uri 'none'; form-action 'none'">
~~~

Read `apps/reader/csp.ts`. Which script may run, and who computed its hash? Why is there one
`style-src-attr` hash, and what keeps it current? (The scenario for R-034 in
`tests/bdd/features/reader/guarded-reader.feature`.)

## Prove it in a browser

~~~bash
pnpm test:e2e
~~~

~~~
 Test Files  2 passed (2)
      Tests  6 passed (6)
~~~

Three of the six are rung 6's. Open `tests/e2e/guarded.e2e.ts`: the reader opens the hostile course in
Chromium and no dialog appears; a script, an event handler and a style are injected into the live page and
the policy refuses each; and the reader never trips its own policy.

## Evaluate

1. The site's policy is L5 on the Assertion Ladder, "Prevented". By whom? What does it cost?
2. A meta tag cannot set `frame-ancestors`. Which attack does that leave open, and whose job is it? (See
   "Deliberately left out" in `RUNG.md`.)
3. An agent proposes `'unsafe-inline'` to fix a styling bug. Name the three places rung 6 would stop it.
